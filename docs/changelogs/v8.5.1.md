# v8.5.1

## Highlights

The CMS gets its overhaul: health probes, structured logging, a real delivery status on push notifications, and three content features (voice over, content filter, age restriction levels) that ship behind feature flags and stay off until a deployment turns them on. The CMS can now authenticate with Firebase through an environment variable, which is what the AWS ECS deployment needs to send notifications at all. No app store release is required: the mobile app only changes version and learns to pick one Firebase project per environment at build time.

## New

- **Notification delivery status.** The Notifications page shows what happened to each broadcast: Sent (Firebase confirmed it), Failed (Firebase rejected it, nobody received it) or Unknown (no answer in time, check the Firebase console before resending). The row is written before Firebase is called, so a crash mid-send can no longer leave a delivered alert without a trace. A failed send keeps the modal open and shows the reason. The app keeps reading only rows with status `sent`.
- **Feature flags** (`FEATURE_VOICE_OVER`, `FEATURE_CONTENT_FILTER`, `FEATURE_AGE_RESTRICTION_LEVELS`). Voice over on encyclopedia articles, the content filter level, and age restriction levels (a minimum age per item, encyclopedia included) are built but disabled by default. While a flag is off its CMS columns are hidden, its endpoints answer 404 and the `/mobile` payloads carry neutral values. See [Upgrade notes](#upgrade-notes) and [FEATURE_FLAGS.md](../../packages/cms/FEATURE_FLAGS.md).
- **Firebase service account from the environment.** `FIREBASE_SERVICE_ACCOUNT_BASE64` holds the service account JSON, base64 encoded, for platforms that cannot mount `firebase-config.json` (AWS ECS). When set it takes priority over `GOOGLE_APPLICATION_CREDENTIALS`.
- **Health probes.** Public `/health` (database check, 503 when down), `/health/live` and `/health/ready` for Docker, load balancers and orchestrators.
- **Monitoring and diagnostics** `/monitoring/*` (health, metrics, per-route response times, slow routes) and `/diagnostics/*` (report, exceptions, memory, timeouts, endpoints) for a logged-in super admin, served with `Cache-Control: no-store`.
- **Structured logging.** JSON logs with `LOG_LEVEL`, optional `LOG_FILE_PATH`, and `SLOW_QUERY_THRESHOLD` / `SLOW_REQUEST_THRESHOLD` warnings. Console logging stays on if the file cannot be written.

## Improvements

- **No duplicate broadcasts.** A notification is retried only when Firebase reports a clean rejection (server unavailable, internal error, network error). A timeout or an unknown error is recorded as Unknown and never resent automatically, so a slow Firebase cannot push the same alert to every user twice.
- **Startup and resilience.** The CMS retries the database connection at startup (5 attempts, 2 to 30 seconds apart), applies a timeout to requests and to external calls, and drains connections for up to 30 seconds on SIGTERM before exiting.
- **Content security policy.** Inline scripts are gone; every page script runs under a per-response nonce. The About banner attribute is escaped and new image URLs are validated.
- **Voice over replacement** keeps the previous audio until the new upload and the database save both succeed, uses unique object names and cleans up failed or late uploads.
- **Survey writes are atomic.** Create, update and delete run in a transaction, lock the parent survey and reject questions that belong to another survey.
- **Operational endpoints are bounded.** Diagnostic state aggregates by route pattern, caps retained routes, errors and string lengths, and expires idle routes, so arbitrary URLs cannot grow memory.
- **Log privacy.** Query strings and fragments are stripped from logged URLs, SQL bind values and raw driver errors are never logged, and `DATABASE_LOGGING=false` is honoured. Public health responses no longer include raw database errors.
- **Container hardening.** The CMS image runs as the unprivileged `node` user and starts Node directly instead of through Yarn, so SIGTERM reaches the shutdown handler.

## Fixes

- **CMS logout** works again: the passport 0.5 `logout()` is synchronous, so the redirect now runs right after it instead of inside a callback that never fired.
- **Surveys on deployed environments.** The mobile survey query joined `oky_user` through the query builder, which failed with a schema-qualified table name. The user's age is now read separately and the age restriction applied in code.
- **Help center** edit, delete and live toggle, and the **category and video** management buttons, work again under the content security policy (inline handlers replaced by bound listeners and links).
- **Encyclopedia** articles are listed by creation date.
- **New articles** get default filter and age options, so they can be saved while the flags are off.
- **Voice over upload** answers with a generic error instead of internal details, and accepts filenames containing a hyphen.
- **Request logs** carry the user id again (resolved after passport populates the session).
- **Reordering** categories, subcategories and articles returns a response to the client.
- **Monitoring database check** has a 5 second deadline and does not write after the client disconnects.
- **Container health probes** read `CMS_PORT` instead of assuming port 5000.

## Backend and API

- **`/mobile` payloads under the flags.** While a flag is off, articles are sent with `voiceOverKey: null`, articles, quizzes, surveys and did you knows with `contentFilter: 0` and `ageRestrictionLevel: 0`, and articles with `isAgeRestricted: false`. Quizzes, surveys and did you knows keep their `isAgeRestricted` toggle.
- **Gated endpoints.** `/api/voice-over/*`, `/api/content-filter` and `/api/age-restriction` answer `404` while their flag is off. Creating or editing an article ignores `contentFilter` and `ageRestrictionLevel` while the matching flag is off.
- **Migration** `1742860800000-add-indexes.sql` adds 42 indexes on the content, notification, user, analytics and event tables. No table or column changes in this release: the `notification.status` column already exists. How to apply it is in the [Upgrade notes](#database-migration).
- **Known issue, pre-existing.** `GET /mobile/notification/:lang` sends no response when no sent notification exists for that language; the client times out. Not fixed in 8.5.1.

## Platform

## Build and tooling

- **CMS Dockerfile.** Both stages run as `USER node` and declare a `HEALTHCHECK` against `/health` on `CMS_PORT`. The production stage starts with `node dist/src/index.js` (`NODE_PATH=/usr/src/app/dist`) instead of `yarn serve`.
- **docker-compose.yml.** The CMS depends on `postgres`, restarts unless stopped, has a 35 second stop grace period and the same health check.
- **TypeORM logging.** With `DATABASE_LOGGING=true` the CMS logs all queries through a slow-query logger using `SLOW_QUERY_THRESHOLD`; with `false` nothing is logged.
- **`yarn format`** runs prettier on the CMS package.
- **CMS documentation** added under `packages/cms/`: `FEATURE_FLAGS.md`, `HEALTH_CHECKS.md`, `MONITORING.md`, `LOGGING_AND_ERROR_HANDLING.md`, `CRASH_ANALYSIS.md`, `DB_QUERY_OPTIMIZATION.md`, `TESTING.md` and `REVIEW_FIXES.md`. `docs/setup.md` and `docs/deployment/aws_deployment.md` cover the Firebase variable and the flags.

## Upgrade notes

### Feature flags

All three features are off after the upgrade. A flag is an environment variable read once when the CMS starts; only the exact string `true` enables it (`1`, `yes`, `TRUE` and an empty value leave it off). The flags are independent, and turning one on or off needs no app build: the app picks up the change the next time it refreshes content from the CMS.

| Flag | Enables | While off |
| --- | --- | --- |
| `FEATURE_VOICE_OVER` | Audio recordings on encyclopedia articles | Voice Over column hidden, `/api/voice-over/*` answers 404, app receives `voiceOverKey: null` |
| `FEATURE_CONTENT_FILTER` | Content filter level on articles, quizzes, surveys and did you knows | Filter column hidden, `/api/content-filter` answers 404, app receives `contentFilter: 0` |
| `FEATURE_AGE_RESTRICTION_LEVELS` | Minimum age per item, encyclopedia articles included | Quiz, survey and did you know pages keep the single Age Restricted toggle; articles have no age restriction; app receives `ageRestrictionLevel: 0` |

**How to set them**

1. Local or Compose: add the lines to `packages/cms/.env`.

   ```env
   FEATURE_VOICE_OVER=true
   FEATURE_CONTENT_FILTER=true
   FEATURE_AGE_RESTRICTION_LEVELS=true
   ```

2. Kubernetes: add them to the CMS container env in `cms.yaml`.

   ```yaml
   - name: FEATURE_VOICE_OVER
     value: 'true'
   - name: FEATURE_CONTENT_FILTER
     value: 'true'
   - name: FEATURE_AGE_RESTRICTION_LEVELS
     value: 'true'
   ```

3. AWS ECS: add the same lines to `project_oky_cms_task_configuration.env` in the configuration S3 bucket, then force a new deployment of the CMS service. The env file is only read when a task starts.

4. Restart the CMS. Nothing applies until it restarts.

**Before enabling, check**

- Voice over needs Firebase Cloud Storage: `STORAGE_BUCKET` and `STORAGE_BASE_URL` must point at the bucket of the same Firebase project as the service account, and the CMS must reach `googleapis.com` (see [AWS deployment](#aws-deployment)).
- Content filter levels come from `contentFilterOptions` in the `@oky/core` common submodule (`packages/core/src/common`). Without them the only level is All.
- Age restriction levels come from `ageRestrictionOptions` in the same submodule. Define the options before turning the flag on, otherwise the only level is All, which is no restriction.
- Age restriction: the old toggle and the new level share the same database columns. Setting a level other than All turns the toggle on; turning the flag off afterwards keeps those toggles on. The toggle on quizzes, surveys and did you knows is always available and not affected by the flag.

**Turning a feature off again.** Set the variable to `false` or remove it, then restart. No data is deleted: voice over files stay in storage and filter or age levels stay in the database, hidden until the flag comes back.

### Database migration

No table or column changes. The one database change is `sql/1742860800000-add-indexes.sql`, 42 indexes that speed up the language and live filters behind most CMS and `/mobile` queries. The CMS runs without them, so the file can be applied before or after the deployment.

**Apply**

1. Connect to the database with `psql` (on AWS, from a host inside the VPC or through the Adminer setup in [adminer.md](../deployment/adminer.md); RDS is not reachable from outside).
2. If `DATABASE_SCHEMA` is not `periodtracker`, replace every `periodtracker.` qualifier in the file first. The file names the schema explicitly so the result does not depend on the connection search path.
3. Run the file:

   ```bash
   psql "$DATABASE_URL" -f sql/1742860800000-add-indexes.sql
   ```

4. Check with `\di periodtracker.idx_*`: 42 indexes.

Every statement is `CREATE INDEX IF NOT EXISTS`, so the file can be run again safely. It was verified on PostgreSQL 16; production and Compose run PostgreSQL 10, where the syntax (including the two partial expression indexes on `app_event`) is supported, but index-build locking on production data was not tested. `CREATE INDEX` blocks writes to the table while it builds; the tables are small, so expect seconds, but run it outside content-editing hours. On Aurora Serverless with 0 minimum ACU the first statement wakes the database; wait rather than retry.

**Keep schema synchronization off.** The entity classes now carry `@Index()` decorators too, applied by TypeORM only when `DATABASE_SYNCHRONIZE=true`. The decorator set is not identical to the SQL file (the SQL adds indexes on users, analytics, events, suggestions and avatar messages that have no decorator), and a synchronize run drops indexes it does not know about. Leave `DATABASE_SYNCHRONIZE=false` in production, as in `.env.dist`.

**Fresh installs.** `sql/initial-setup.sql` was not updated with the indexes; run the index file after it.

**Rollback.** No data changes, so dropping the indexes restores the previous state: `DROP INDEX IF EXISTS periodtracker.<name>` for each `idx_*` name in the file. Downgrading the CMS image to 8.5.0 does not require dropping them.

### Firebase configuration

The CMS uses Firebase for push notifications (Cloud Messaging, one topic per language) and for voice over audio (Cloud Storage, only with `FEATURE_VOICE_OVER`). Both authenticate with a service account of the Firebase project. 8.5.1 adds a second way to hand that service account to the CMS, for platforms that cannot mount a file.

**One project per environment.** Use a separate Firebase project for development and production so test notifications and crashes never reach real users. The app and the CMS must point at the same project, otherwise sends fail with `messaging/mismatched-credential`.

| Component | Production | Development |
| --- | --- | --- |
| Android app | `app/src/resources/google-services.json` | `google-services.json.dev` next to it |
| iOS app | `app/src/resources/GoogleService-Info.plist` | `GoogleService-Info.plist.dev` next to it |
| CMS credential | Service account key of the production project | Service account key of the development project |
| CMS storage | `STORAGE_BUCKET` and `STORAGE_BASE_URL` of the production bucket | Same, development bucket |

**Get the service account key.** Firebase console, Project settings, Service accounts, Generate new private key. Save the JSON as `firebase-config.json`. It is a secret: never commit it, store it like the database password.

**Option A: key file (Docker Compose, Kubernetes).** Unchanged from 8.5.0. The CMS image sets `GOOGLE_APPLICATION_CREDENTIALS=/usr/src/app/packages/cms/firebase-config.json`; Compose expects the file in `packages/cms/`, and the Kubernetes manifest mounts it from the `firebase-config` secret at `/periodtracker/config/firebase-config.json`. Leave `FIREBASE_SERVICE_ACCOUNT_BASE64` empty.

**Option B: environment variable (AWS ECS, any env-only platform).** Encode the key on one line and pass it as `FIREBASE_SERVICE_ACCOUNT_BASE64`:

```bash
base64 -i firebase-config.json | tr -d '\n'
```

```env
FIREBASE_SERVICE_ACCOUNT_BASE64=<one-line base64 of the JSON>
```

When the variable is set it takes priority over the key file; when empty the CMS falls back to the file. A value that is not valid base64 JSON stops the CMS at startup with `FIREBASE_SERVICE_ACCOUNT_BASE64 is not a base64 encoded service account JSON file`; the value itself is never logged. `GOOGLE_APPLICATION_CREDENTIALS` stays set by the image, which is harmless.

**Storage (voice over only).**

```env
STORAGE_BUCKET=gs://<project>.appspot.com
STORAGE_BASE_URL=https://firebasestorage.googleapis.com/v0/b/<project>.appspot.com
FEATURE_VOICE_OVER=true
```

**Verify after deployment.** Send a test notification from the Notifications page and read the status badge. The message shown in the modal names the cause:

| Message in the CMS | Cause | Fix |
| --- | --- | --- |
| The CMS could not reach Firebase, check the server network connection | No outbound route to Google APIs | See [AWS deployment](#aws-deployment) |
| The CMS could not authenticate with Firebase | Key invalid, revoked or wrongly encoded | Regenerate and re-encode the key |
| The Firebase credentials configured for this CMS belong to a different project | Service account and app files from different projects | Use the key of the app's project |
| Firebase did not answer in time (status Unknown) | Timeout, often a firewall dropping packets | Check egress, then the Firebase console before resending |

### AWS deployment

The CMS task on ECS Fargate currently has no route to Firebase. [aws_deployment.md](../deployment/aws_deployment.md) describes the tasks in private subnets with VPC endpoints for S3, CloudWatch Logs and ECR only, and states that there is no NAT Gateway to the public internet. Google APIs are not AWS services, so no VPC endpoint can serve them. Until egress exists, every notification ends as Failed with "The CMS could not reach Firebase" (or Unknown on a timeout) and voice over uploads fail, whatever credential is configured.

**What the CMS must reach.** Outbound HTTPS (TCP 443) and DNS resolution for:

| Host | Used for |
| --- | --- |
| `oauth2.googleapis.com` | Exchanging the service account key for an access token (every call) |
| `fcm.googleapis.com` | Sending push notifications |
| `storage.googleapis.com`, `firebasestorage.googleapis.com` | Voice over files (only with `FEATURE_VOICE_OVER`) |

Google's IP ranges change, so allow the hostnames or `0.0.0.0/0` on port 443 rather than fixed addresses.

**Option 1, recommended: NAT Gateway.** Keeps the tasks in the private subnets.

1. Allocate an Elastic IP and create a NAT Gateway in a public subnet (one per Availability Zone for resilience, one is enough to start).
2. In the route table of each private subnet used by the ECS tasks, add `0.0.0.0/0` pointing at the NAT Gateway. The existing S3 gateway endpoint route stays and keeps S3 traffic private.
3. Check the CMS task security group allows outbound TCP 443 to `0.0.0.0/0` (the AWS default egress rule does; keep it if it was narrowed).
4. Confirm the VPC has DNS resolution and DNS hostnames enabled (the default).

The API task gets the same outbound path; it does not need it today but is not harmed. A NAT Gateway bills per hour and per GB; notification traffic is negligible.

**Option 2: public subnet.** Move the CMS service to the public subnets with `assignPublicIp: ENABLED` in its network configuration. Inbound stays restricted to the ALB by the task security group. Cheaper, but the task holds a public IP, so prefer Option 1.

Not an option: PrivateLink or VPC endpoints (Google is not reachable through them), an egress-only internet gateway (IPv6 only), or a proxy inside the VPC unless one is run and maintained.

**Task configuration.** In `project_oky_cms_task_configuration.env` in the configuration S3 bucket, add `FIREBASE_SERVICE_ACCOUNT_BASE64` (see above), the three `FEATURE_*` flags (as `false` unless the content is ready) and, optionally, `LOG_LEVEL`, `SLOW_QUERY_THRESHOLD` and `SLOW_REQUEST_THRESHOLD`. The bucket is readable only by the task roles, which is acceptable for the key; to keep it out of the env file, store the base64 value in Secrets Manager or SSM Parameter Store and reference it from the task definition with `secrets` / `valueFrom`, granting the task execution role `secretsmanager:GetSecretValue` or `ssm:GetParameters` on that one resource.

**Task definition.** Set `stopTimeout` on the CMS container to 35 seconds so the 30 second connection drain can finish (the Fargate default is 30). Point the CMS target group health check at `/health/ready` (or `/health`); the Docker `HEALTHCHECK` is ignored by Fargate, the ALB check is what counts.

**Deploy.** Build and push the CMS image with a new tag, register a new task definition revision, then update the service with `--force-new-deployment` so the env file is read again:

```bash
aws ecs update-service --cluster project-oky-ecs-cluster \
  --service project-oky-ecs-cms-task-service \
  --task-definition project-oky-ecs-cms-task:<revision> \
  --force-new-deployment --region eu-west-2
```

**Verify.** CloudWatch Logs for the CMS task should show `Firebase notification sent` with a `messageId` after a test notification, and the Notifications page should show it as Sent.
